## 二、技术方案要点

- 形态：fnOS Native `.fpk`，Go 1.23 单静态二进制，无 Docker。
- 管理面：只经统一网关 Unix Socket（`app.sock`，`/app/fngate`），不监听管理 TCP 端口。
- 状态：单一 `state.json`（`schema_version=1`）+ 独立 `secrets/`（0700 / 0600），原子写、失败回滚、升级迁移前备份。
- 反代：`Listener`（端口/协议/TLS）+ `Route`（域名/路径/后端）双层；增量 Apply；`GetCertificate` 动态解析，证书续期零重启生效。
- 证书：统一 `CertificateResolver`，四来源（manual / fnos / acme / selfsigned），反代按 `cert_id` 引用。
- 安全：同源 + CSRF；私钥与 DNS 凭据不进 state.json、不进 API 响应、不进日志。

## 四、每个里程碑的执行循环

1. 写代码（按模块增量）
2. 验证：`go vet ./...` → `go test ./...` → 本地调试模式冒烟（关键 API）
3. 汇报一行结果，再进入下一模块

## 五、已知的工程约束（来自参考项目实测）

- 管理面必须走统一网关 Socket，`protocol: ""` + `control.accessPerm: hidden`，否则 HTTPS 访问飞牛时 iframe 混合内容白屏。
- Windows 下 `fnpack` 会丢 Unix 执行位，打包后必须重建两层 tar 并显式写 `0755/0644`，同时重算 `manifest.checksum`（= `app.tgz` 的 MD5）。
- 静态资源引用需带 `?v=<版本号>`，否则升级后出现「新 HTML + 旧 JS」。
- 同一端口只能一种协议；绑定失败必须可见化，不允许静默失败。
- fnOS 系统证书路径来自社区资料，属内部实现，需多路径探测 + 解析失败降级为手动上传。

## 六、不在本机可验证的部分

- fnOS 真机安装、统一网关接入、桌面图标、80/443 绑定能力、`cmd/main status` 生命周期。
- 真实路由器的 UPnP 映射与自动补发。
- Let's Encrypt 生产签发（本机仅能验证订单状态机；staging 签发需公网 DNS）。
- 这部分以「本地可编译 + 单元测试 + API 冒烟 + 产物结构校验」覆盖，交付时明确列为需在真机验证的清单。
